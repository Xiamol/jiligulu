# 2026-10-02 流畅度与 AI 费用优化

本轮保持 0.6.2，本地同签名 Release 验收，尚未发布。价格按用户提供的元/百万 tokens：命中 0.02、未命中 1、输出 4，不承诺长期价格。

## 先算费用

费用 = (命中 token × 0.02 + 未命中 token × 1 + 输出 token × 4) / 1,000,000。
一个未命中 token 的费用等于50个命中 token；一个输出 token 等于200个命中 token。
只看百分比会误判。输出均为300 token时：

|输入|命中率|估算元/轮|
|---|---:|---:|
|10,000|55%|0.00581|
|20,000|90%|0.00356|
|100,000|95%|0.00810|

## 选择与边界

1. 普通 DeepSeekClient 显式 thinking disabled；图像识别原来已禁用。low 仍是思考，不等于 disabled。保留 AI 语义理解和可修改草稿，不删用户历史，不缩短现有闲聊人设字数要求，不设置可能截断 JSON 的激进输出上限。
2. 连续聊天较多的使用偏好下，保留最低60条历史，分批增长到139（batch80），再整体裁切。24小时范围与原文保持。对比上一轮60～79，减少整段前缀重新计算的频率。不是每轮额外重传全部旧历史，也不是永久记忆。
3. 缓存冷掉时更长历史首轮较贵，更多上下文不保证更好回答。长期应观察“每轮元数/未命中token/输出token”，不以命中百分比单独评价。必要时再按真实使用调整窗口。
4. 新增“阿噜的用量小账本”：设置 → 数据 → AI服务中查看今天/累计的本机用量和费用。包含对话、分类、图片请求，每次重试分别计数；输出不重复叠加 reasoning。没有返回用量的请求单列提示。只保存数字汇总，不存请求正文、图片、Key。不是服务商完整账单，也不回填旧版本消费。
5. UI 历史与AI上下文独立：聊天首屏仅读最近80条，顶部按需加载更早80条。主键游标无OFFSET扫描，解析草稿放后台线程；旧页追加不触发自动滚底，新消息仍自动跟随。Lazy按消息类型复用布局。

## 构造样本的实际调用

使用同一系统规则，未带用户真实聊天/账单，3组default/disabled对照；所有回答非空，补记与多笔拆分金额收支一致。

|输入|默认输出token|disabled输出token|默认耗时秒|disabled耗时秒|
|---|---:|---:|---:|---:|
|闲聊|62|28|0.96|1.02|
|昨天中午吃饭9元|237|101|1.91|0.86|
|早餐8、地铁3、工资2000|380|220|2.07|1.57|

含推理的输出总量679→349，仅为3个构造样本，不代表所有任务质量、平均速度或固定节省比例。不同请求的缓存也会波动，不能把所有费用差归因于思考开关。原始数字在 AI_COST_PROBE_2026_10_02.json。

## 离线窗口比较（非真实计费）

脚本 tools/analyze_ai_cost.py 可复现，假设600轮、历史每消息40 tokens、固定前缀2400、动态600、输出80，缓存连续可复用。旧batch20约0.7896元，batch80约0.7075元，batch120约0.7048元；batch80相近但历史更短。batch240命中率更高但约0.7194元，已经更贵。
若每10轮强制冷缓存，batch20约0.9328元，batch80约1.0121元，排序逆转。这是说明“更长并非总省钱”，不是对服务端缓存过期时间的假设。
