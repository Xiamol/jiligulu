## AI 用量基线与优化边界

用户口述的实际观察（尚未从账单/接口 usage 独立复核）：

- 长对话缓存命中率约 **75%**；短对话约 **55%**。
- 当天大约 **50 万 token**，主要用于闲聊，记账相对少。
- 希望进一步提高缓存利用率、降低实际费用，同时保留正常闲聊体验。

尚不明确：50 万是否包含输入/输出/思考 token；命中率是单次、简单平均还是按输入 token 加权；时段与实际费用。不能直接从总 token 推断花费或承诺节省百分比。

已确认先统计、再优化且不牺牲记忆；以下技术调查顺序为落地建议，尚未实施：

1. 汇总每次请求的缓存命中输入、未命中输入、输出/思考 token、失败与重试开销；按 token 加权统计命中率，并区分闲聊、记账和图片任务。
2. 检查静态前缀、历史序列化、类别顺序与窗口滚动是否打断缓存；不要改回曾引发空白响应的纯文本 assistant 历史。
3. 对闲聊中不必要的动态账本内容和输出冗余做受控对照，不能破坏用户需要的账本关联和对话记忆。
4. 核对思考模式：当前客户端未显式传 thinking/reasoning_effort；查阅时官方说明默认启用思考。先看实际 usage，再比较普通闲聊的不同思考档位，不能直接假定关闭即可无损省钱。
5. 目标是实际费用与体验改善，不是用填充长提示词等方式单纯抬高命中率。系统缓存复用本身不能由 App 强制保证。

当前实现只在日志记录 cache hit/miss，尚无应用内费用看板或每日汇总。增加统计面板是助手建议，未被用户单独指定 UI。

## 已实现 A：远程公告（待手机验收）

实现说明及运营方法：`docs/ANNOUNCEMENTS.md`。独立内容分支 `announcements` 的空公告源已接通，未发送实际公告；新功能 APK 尚未作为 GitHub Release 发布。

### 用户明确提出的行为

- 进入应用时像更新提醒一样弹出公告。
- 选择“关闭”：下一次**冷启动**仍主动弹出。
- 选择“不再显示”：下次冷启动不再显示该公告。
- 首页增加好看的公告栏，可放节假日祝福等内容。
- 发新公告不应要求每次发 APK、让用户重新安装。

### 已确认方向与待落地细节

- 可行性高。App 首次需要安装一次包含公告能力的新版本；此后修改独立 HTTPS 公告数据即可，不依赖新增 Release/版本号。
- 可先用 GitHub 托管的静态 JSON（或 GitHub Pages）；若访问稳定性不理想，可换独立 HTTPS 静态托管。内容管理与 App 更新仓库可以共用 GitHub，但数据文件和版本更新逻辑分开。
- 公告建议包含独立 id、标题、正文、生效/截止时间、排序等。初期可直接编辑文件，后续需要再做发布表单/管理页。App 只读，不内置公告发布凭据。
- **已确认**“不再显示”按公告 id 记住，仅禁止这条自动弹出；新的公告仍可弹。按钮使用“这条不再弹出”，减少与首页公告栏的歧义。
- **已确认**不再弹出的公告仍能在首页公告栏主动查看；正文小改保持 id，真正新的公告使用新 id。
- 同一次进程会话只弹一次，页面切换/切后台回来/Activity 重建不算冷启动；关闭仅记录本次会话，不写永久屏蔽。
- 公告与更新弹窗排队，避免叠两个弹窗；过期公告不弹。拉取异步进行，断网不阻塞启动，可展示缓存的有效公告。
- 首页方向已确认：阿噜下方的奶油紫便签卡，标题摘要、节日点缀、点击全文，不遮挡标题与常驻阿噜。具体视觉细节在实施设计时细化。
- 不是系统通知推送：用户打开 App 拉取并展示。未打开 App 时不承诺送达；将来的后台推送需另行设计。
- 公告本身不需要调用 AI，不消耗 DeepSeek token。

## B：语音输入界面已实现，vivo 系统识别不可用，等待替代路线

用户在无法连接手机时明确选择“先实现系统语音方案”。已实现 Android SpeechRecognizer 接入、按住录音/松开识别、可编辑回填、手动发送、权限与错误提示、离开页面取消。原先仅以模拟识别结果验证交互；现在的真机结论见下段，未接第三方语音服务。

2026-09-24 更新：用户已在 vivo 试用，麦克风权限正常，但默认 CopilotRecognitionService 在就绪前立即返回错误码 5；去掉可选参数的最小请求也失败。系统方案在本机未跑通，不再继续反复尝试。已补输入模式持久化，暂时文字编辑不覆盖主动选择的语音偏好。待用户选择离线识别、独立云端转写或暂缓；不能记成“语音已修好”。

用户目的：减少打字，通过说话完成对话记账；询问 DeepSeek 是否能直接识别音频以及实现难度。

2026-09-23 查阅的 DeepSeek 官方公开 Chat Completions / Responses API 列出文字与图片输入，未列出可直接使用的音频输入或语音转写接口。应按“语音识别服务转文字，再交给 DeepSeek”的方案评估，不把“支持多模态/图片”当成支持音频。未来实施前复核文档。

已确认首版流程：**按住说话 → 松开转文字 → 显示可修改的文字 → 用户发送 → 可编辑草稿 → 用户确认入账**。不将“转写后直接生成草稿”当作首版默认；不可绕过现有金额、日期与确认保护。用户没有要求全双工语音聊天或阿噜语音播报。

- 系统 SpeechRecognizer：接入较轻，可优先检测设备上是否可用；离线能力并非每台手机都有，某些实现会联网，不能承诺免费离线且全机型通用。
- 独立语音转写服务：可减少对手机预装识别服务的依赖，但增加服务接入、音频网络请求及按供应商规则计算的费用；供应商尚未选定。
- 自带离线识别模型：包体、模型下载、性能及适配成本更高，可后置。
- 实施前先在用户 vivo 手机上检测中文识别可用性；录音只由明确操作开始，有结束/取消反馈，数额与时间识别结果仍需可校正。

## 仍未排进近期的旧提案

云同步、独立日历页、预算超支通知、滑动时间轴、离线 OCR、更多彩蛋、API Key 存储加固、Baseline Profile 等未在这次排定实施；不要视为已授权全部开工。
