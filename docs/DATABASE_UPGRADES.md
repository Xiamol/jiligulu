# 数据库升级与保数据验证

当前版本为 **1.1.0 / versionCode 27**。数据库仍为 Room v6，文件名仍是 `jiligulu.db`，包名仍是 `com.jiligulu.app`；本次不增加数据库版本，继续沿用旧安装包签名。

从 1.0.0、1.0.1 或 1.0.13 更新时直接覆盖安装，不要卸载或清除应用存储。已有账单、分类、预算、照片、聊天、个人记忆及设置应保留；移除 API 花费统计时只清理废弃的计价与用量数据，不清空正常业务数据。

## 当前迁移

- v1 → v2：给分类表增加 `iconSvg`，不改写已有分类或账单。
- v2 → v3：新增预算表。
- v3 → v4：新增聊天记录表，账单、分类与预算表保留。
- v4 → v5：增加账单软删除时间 `deletedAt`，旧账默认仍是正常账单。
- v5 → v6：分类增加 `deletable`，合并英文种子及重复中文分类，先转移所有引用（含回收站账单），再删除重复项；补齐不可删的「待定」。
- `AppDatabase.ALL_MIGRATIONS` 注册完整路径。没有破坏式升级或降级兜底；缺少路径时拒绝打开并保留数据库，不删库重新开始。
- 首装种子只在建库事务中写入，升级不重新灌入整套默认分类。另有一次性新增预设补齐：保留同名自定义分类，已完成补齐后不会重新添加后来被用户删除的预设。

## 后续更新的检查点

1. 保持包名、数据库文件名、DataStore 文件名和签名一致，递增 versionCode。用户通过覆盖安装更新。
2. 修改 Room schema 时增加数据库版本与明确 Migration，保留旧的导出 schema；不修改历史 schema 冒充兼容。
3. 运行 `DatabaseUpgradeTest`：从真实历史 schema 建库、写入样例账单和附加字段，然后让 Room 实际升级并验证数据。
4. 新版本仍应覆盖聊天记录恢复、未确认草稿恢复、已确认草稿幂等、失败整批回滚。金额、时间和未编辑字段要分别断言。
5. 真机发布前再用旧 APK 录入样例数据，覆盖安装新 APK 检查。卸载或清除应用存储会删除本机数据，不能用卸载重装代替升级验收。

## 一次确认的事务边界

`ChatHistoryRepository.confirmDraftAtomically` 把最终草稿（含确认时冻结的默认时间）、新增分类、全部账单和 CONFIRMED 状态一起提交。任何一步失败均回滚；重新确认已成功的历史卡只返回已存条数，不再次入账。旧 DISMISSED 草稿可编辑确认，DELETED 草稿不可编辑确认。

清空聊天是显式确认后的独立操作，只清聊天数据，保留未入账草稿与所有账本表。存在进行中的 AI 回复时拒绝清空；设置操作与清理共享串行锁，避免已清理的操作卡继续生效。

账单详情编辑使用目标列 UPDATE，只更新仍在账本中的记录。可保存金额、细则名称、时间、备注与照片；未编辑的值沿用，来源、分类和 AI 原始输入保留。

本机制保护升级和应用内操作中的已有数据；它不等同于独立的离线备份或跨设备同步。
