## 架构判断

当前单应用模块、Compose → ViewModel → Repository → Room/DataStore 的结构足以支撑现有规模，不需要换框架或拆成很多 Gradle 模块。真正暴露的问题集中在卡片状态、跨持久层提交、提醒调度及旧数据兼容，而不是页面排版本身。

本轮把提醒拆成 Scheduler、Engine、Notifications 与 Receiver，保留一个系统触发源；旧 Worker 仅兼容已存任务。分类徽章与设置弹窗也统一为共享组件，避免每个页面各自兜底。

仍有维护债：`AiRepository` 与 `ChatViewModel` 较大，部分持久卡片 DTO 仍放在 `ui/chat` 并被数据层引用。继续增加多种 AI 操作时，适合把卡片协议、纯解析和执行器分别移到 domain/data；本轮不在修复行为的同时做大范围文件迁移。

## 修复的实际缺陷

- 已取消 AI 指令卡重进聊天后复活、未知指令种类被当作 UPDATE、部分成功卡再次执行时错用位置计数。
- 仅改账单名称时因金额缺省为 0 被拒；显式改时间被忽略；旧草稿确认时把已删除的分类重新建回来。
- 网络失败时，把改账或设置请求误交给仅支持新增的离线解析器。现在保守拒绝这种降级，并保留普通新增账单的离线草稿能力。
- 手动恢复账单未把失效分类转入「待定」；旧详情编辑器能改到已移入回收站的账单。
- 旧提醒关闭请求可能取消后来开启的闹钟；生成水杯和推进下次到期时间分开写，可能留下重复触发窗口。
- 可选启动清理吞协程取消或等待系统调度过久。现在保留取消语义，可选维护并行、分别限时。
- 设置页关于数据去向的描述不符合实际，现明确说明 AI 消息及部分账本上下文会发送给 DeepSeek。
- 清空聊天的 Compose 端到端测试捕获了界面效果协程与 Room 事务上下文的冲突；清理改由 SettingsViewModel 发起，未放开主线程数据库访问，实际按钮的取消、确认、保留账单与重进聊天用例已通过。
